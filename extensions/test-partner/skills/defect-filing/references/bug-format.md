# 缺陷正文格式规范（从小铁资产移植）

> 来源：`qiqi_AI蓝牙项目/PLAN/tapd/BUG_FORMAT.md`（工作区权威）＋
> `.agents/skills/tapd/skills/write/SKILL.md` 的 C1 流程。
> 本文是**移植件**：结构与三条硬纪律一字不改，只把「小铁专用」的字段默认值
> 抽到 `field-defaults.json`（按项目配置），以及删掉本仓没有的脚本入口。
>
> 标准样例（真实已分配单号）：<https://www.tapd.cn/67600006/bugtrace/bugs/view/1167600006001009428>

---

## 1. 标题

```
{项目前缀}{模块/分类}：{问题描述（一句话）}
```

- 项目前缀从 `field-defaults.json` 的 `title_prefix` 取，不在这里写死。
- 模块/分类：端侧语音、稳定性、触摸/UI、后台接口 …
- 问题描述：**现象 + 影响，不写根因**（根因归第 6 段）。

示例：`【小铁IP机器人】端侧语音：物理按键触发监听后无识别结果和回复`

---

## 2. 正文结构：固定 6 段，顺序不可变

```
环境 → 复现步骤 → 期望结果 → 实际结果 → 日志证据 → 初步判断
```

对应 heading id `_1` … `_6`。**这 6 个段名与顺序是这份规范的全部刚性所在**：
不许加段、不许改名、不许调序、不许把「附件①②」「对照日志」「优先级建议」
另立成段。渲染器 `scripts/render_draft.py` 直接按这个序列校验，改一个字就判红。

### 2.1 环境（`<h2 id="_1">环境</h2>`）

无序列表，按被测对象实填，常见项：

- 版本标识（固件版本 / 编译时间 / bin MD5；服务端则是部署 commit 或镜像 digest）
- 硬件 / 样机编号 / 靶机地址
- 触发方式 / 测试模式
- 日志采集方式

### 2.2 复现步骤（`<h2 id="_2">`）

有序列表，3–6 步，可独立复现。

**铁律（2026-06-01 立，因违反过一次）**：

- 只写**本人本会话实际操作过、且确实复现到**的步骤序列。
- **严禁把「从日志反推出来的触发机制」当复现步骤写**——机制归第 6 段，不进步骤。
- 有必需前置条件单列「前置：…」，不要混进操作步骤。
- **一条缺陷只给一条实操路径**；别的场景在第 6 段一句话带过并指向其日志。

渲染器要求草稿显式带 `"repro_verified": true`；没实操过就填 `false`，
它会直接拦下来并告诉你该把这段挪去第 6 段。

### 2.3 期望结果 / 2.4 实际结果

各一段，对比清晰，**不写解决方案**。

### 2.5 日志证据（`<h2 id="_5">`）—— 核心格式

```html
<ul>
<li>日志文件：{附件链接 或 <code>logs/xxx.log</code> 占位}</li>
<li>关键现象：</li>
<li>{现象分类 A}：<ul><li><code>TAG: 关键 log 行</code></li></ul></li>
<li>{现象分类 B}：<ul><li><code>…</code></li></ul></li>
</ul>
```

规则：

- **每缺陷只挂 1 个主复现 log**，对应该缺陷那一条复现路径。禁止塞「对照日志」
  「设备 B」等无关附件。渲染器把 `log` 收成单值字段，给数组即判红。
- 「关键现象」按**链路分段**（如：按键正常 / 监听启动 / 上行正常 / 业务回包缺失），
  每段 1–4 条摘录，可变部分用 `…` 省略。
- **禁止**正文另加大段 `<pre>` 日志块——完整 log 走附件。

> ⚠ **附件上传在本仓这条通道上不可用**（当版实证）：容器内的官方
> `mcp-server-tapd==8.0.80` 全量 43 个工具里**没有任何附件上传工具**
> （只有只读的 `get_entity_attachments` / `get_image`）。按 0027 的降级条款，
> log 以**可访问链接或正文占位路径**承载，不因附件卡住整条链。
> 用户要真附件时，由用户自己在 TAPD 页面上传。

### 2.6 初步判断 / 根因（`<h2 id="_6">`）

一段话，测试视角归纳（哪段链路正常、哪段异常）。

- **没定位到根因**：只做测试视角归纳，不臆测修复方案。
- **已看码定位到根因**：写明根因（`文件:行号`）+ 一句修复方向。这是已验证的
  可执行信息，**必须保留**——「说人话」不等于把它删掉。
- 仍放在本段，**不另立 heading、不破坏 6 段结构**。

优先级由 TAPD 字段 `priority_label` 承载，**不进正文**。

## 3. 字段：一律不写字段编号

TAPD 自定义字段的编号**按工作项类型各排各的号**——同一项目里「需求第 1 栏」
与「缺陷第 1 栏」是两个完全不同的字段。硬编码 `custom_field_N` 是已被实证
会静默腐烂的写法（`.agents/skills/tapd/config.yaml` 2026-08-03 全量复核：
声明的 6 栏里 5 栏是错的）。

**本 skill 的做法（比"现场查"更强的一档）**：自定义字段一律走**别名**
`cus_<字段中文名>`，由 TAPD 后台自己转义成 `custom_field_*`
（锚：`mcp_server_tapd/server.py:753` 建单工具的 docstring
「`cus_{$自定义字段别名}`：参数名会由后台自动转义为 `custom_field_*`」）。
草稿里出现 `custom_field_数字` 一律判红。

**现场查通道的真实边界（别抄错）**：`get_entity_custom_fields` 的
`entity_type` 只支持 `stories / tasks / iterations / tcases`
（锚：`server.py:307` docstring），**不支持 bug**。所以缺陷侧
「现场查编号」这条路在这个工具面上**根本不存在**，只有别名一条路；
真需要看编号时，让用户在 TAPD 页面上核对，不要猜、不要从需求侧的编号外推。

---

## 4. 禁止事项

- 改写第 2 节的 6 段结构（不加「附件①②」、不加对照 log 节、正文不写优先级建议）
- 正文内嵌大段 `<pre>` 日志摘录
- 未经用户确认就调任何写工具
- 一个缺陷混合多个不相关的复现场景
- 草稿里出现 `custom_field_<数字>`
