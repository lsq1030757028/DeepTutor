# 缺陷提单

把 run 里**判红的用例**变成缺陷。链路固定四步，**一步都不许跳**：

取材 → 结构化归因 → 预览 → `ask_user` 确认 → 提交。

## 零自动提单（这是红线，不是偏好）

**没有任何一条路径允许不经用户确认就写 TAPD。** 工程稿 §7 的裁决原文是「缺陷根因出口 IN，
**零自动提单**」。你可以整理、可以建议、可以把草稿写得很完整，但按下提交的那一下必须是用户。

当前 TAPD 通道**只放行了两个只读工具**（`get_stories_or_tasks` / `get_stories_fields_info`）。
所以今天这条 skill 走到第四步会**停在确认卡上并如实说明提交通道尚未放行** —— 不许假装提交成功，
也不许把草稿内容塞进聊天里说"你自己复制去提"当作完成。

放行写工具的次序由 `server/journey/defect_exit.write_release_gate` 机械把关：
**写工具必须与确认闸同批放行**，顺序反了那道闸会判红。

## 第一步 · 取材

只从**本次 run 的产物**取，不从记忆、不从上一轮：

- `defect_draft.json`（由 `defect_exit.build_drafts` 产出，在批次目录下）
- `results.jsonl` 里该用例的失败断言明细
- `transcript.json` 里真打过的请求

**只有 `failed` 出草稿。** `blocked` 是环境问题不是缺陷，`observed` 是探测层没有判决权，
`skipped` 连跑都没跑 —— 这三类各自的条数在 `excluded_counts` 里，**汇报时要一起念**，
否则"这轮只有 1 条缺陷"听起来像好消息，实际可能有 8 条被挡在门外。

## 第二步 · 结构化归因

草稿里的 `root_cause` 是**空的**，`root_cause_status = pending_human`。这是故意的：
自动生成的根因读起来像结论，实际是把"我们没查"包装成"我们查过了"，比没有根因更糟。

你要做的是**基于证据**把它填上，且必须能回答：

| 栏 | 填什么 | 不许填什么 |
|---|---|---|
| `phenomenon` | 用户看到什么（断言层面的事实） | 形容词、"不符合预期" |
| `root_cause` | 技术根因，能锚到 `文件:行` 或具体接口/字段的就锚 | 猜测；查不到就写「未定位」并说清查到哪一步 |
| `layer` | 从 `layer_candidates` 里选一个 | 自造新词（词表与 bug-bank 同源） |
| `repro` | 能照着复现的步骤（草稿里已带真打过的请求） | 「见日志」 |

**归因查不到就写"未定位"，并说明查到哪一步为止。** 一条诚实的"未定位"比一条像模像样的
错误根因有用得多 —— 后者会让人照着它去改错的地方。

## 第三步 · 预览

按固定格式把每条缺陷完整渲染出来给用户看，**一条一屏**，不要摘要成一行标题。
预览里必须包含：标题 / 现象 / 根因 / 归属层 / 复现路径 / 证据指针 / 关联需求号。

字段的项目默认值（工作区、需求关联、处理人）从**运行时配置**取，
**不许硬编码进本 skill** —— 硬编码的默认值会跟着 skill 被复制到别的项目，
然后把缺陷提到错误的工作区里。

## 第四步 · `ask_user` 确认

用 `ask_user` 出确认卡：

- **逐条勾选**，不是"全部提交"一个按钮 —— 用户常常只认其中几条；
- **默认一条都不勾**（空选是合法答案：看过并决定都不提，与"这道闸没走"必须可分）；
- 卡上写清**提交后会发生什么**（在哪个工作区建单、谁是处理人、能不能撤）。

用户答完之前，**不许调用任何 TAPD 写工具**。用户没答 = 没授权，不是默认允许。

## 第五步 · 提交与回执

提交成功后回**可点开的 TAPD 链接**，并把 `submission.tapd_ref` 写回草稿。
提交失败要分清两种错并分别说：**通道不通**（我们的问题）和 **TAPD 拒绝**（字段/权限问题）——
合并成一句"提单失败"会让人查错方向。

## 与 bug-bank 的关系

TAPD 是给项目团队看的单；`bug-bank/` 是跨项目的缺陷资产库，**两者都要**。
工作区规范：缺陷统一入 `bug-bank/` 并按其 README 资产化，修复未资产化不闭环。
本 skill 只负责 TAPD 这一侧，入库走 `bug-bank/add.py`，**不要在这里另建台账**。
