# 缺陷提单

链路固定，**一步都不许跳**：

取材 → 结构化归因 → 预览 → `ask_user` 确认 → 提交。

配套四份文件（用 `read_skill` 按需取）：

| 文件 | 是什么 |
|---|---|
| `references/bug-format.md` | 正文格式规范（从小铁资产移植）：六段结构与三条硬纪律的人类可读版 |
| `references/field-defaults.json` | 项目字段默认值（前缀、报告人、候选值表）。**没有字段编号，是故意的** |
| `scripts/render_draft.py` | 草稿 → 预览。三条硬纪律在这里是判红（exit 2），不是叮嘱 |
| `references/example-draft.json` | 一份跑得通的样例草稿，照它的形状填 |

## 零自动提单（这是红线，不是偏好）

**没有任何一条路径允许不经用户确认就写 TAPD。** 工程稿 §7 的裁决原文是「缺陷根因出口 IN，
**零自动提单**」。你可以整理、可以建议、可以把草稿写得很完整，但按下提交的那一下必须是用户。

当前 TAPD 通道**只放行了两个只读工具**（`get_stories_or_tasks` / `get_stories_fields_info`）。
所以今天这条 skill 走到第四步会**停在确认卡上并如实说明提交通道尚未放行** —— 不许假装提交成功，
也不许把草稿内容塞进聊天里说"你自己复制去提"当作完成；正文照给，但要说清单还没建。

放行写工具的次序由两道闸机械把关，**写工具必须与确认闸同批放行**，顺序反了就判红：

- `server/journey/defect_exit.write_release_gate`：判**运行时**放行的工具面（不在只读白名单里的一律按写处理）；
- `tests/test_defect_write_gate.py`：判**仓里六处白名单定义点**，任一处混进写工具、
  或冒出没人看住的第七处定义点，都红。

附件也说清楚：官方 `mcp-server-tapd` 全量 43 个工具里**没有任何附件上传工具**
（只有只读的 `get_entity_attachments` / `get_image`，2026-08-12 无截断枚举核过）。
按 0027 降级条款，log 以**可访问链接或正文占位路径**承载，用户要真附件自己上传，
**不因附件卡住整条链**。

## 第一步 · 取材

两个入口，优先走前者：

**A. 旅程线（有 run 结果时只能走这条）**——只从**本次 run 的产物**取，不从记忆、不从上一轮：

- `defect_draft.json`（由 `defect_exit.build_drafts` 产出，在批次目录下）
- `results.jsonl` 里该用例的失败断言明细
- `transcript.json` 里真打过的请求

**只有 `failed` 出草稿。** `blocked` 是环境问题不是缺陷，`observed` 是探测层没有判决权，
`skipped` 连跑都没跑 —— 这三类各自的条数在 `excluded_counts` 里，**汇报时要一起念**，
否则"这轮只有 1 条缺陷"听起来像好消息，实际可能有 8 条被挡在门外。

**B. 排查线（没有 run，问题是在会话/日志里查出来的）**——从本会话真跑过的命令与日志取。
这条线没有产物兜底，所以对复现步骤的要求更硬：只写**你实际操作过、且确实复现到**的那条路径。

## 第二步 · 结构化归因

`defect_draft.json` 里的 `root_cause` 是**空的**，`root_cause_status = pending_human`。这是故意的：
自动生成的根因读起来像结论，实际是把"我们没查"包装成"我们查过了"，比没有根因更糟。

你要做的是**基于证据**把它填上，且必须能回答：

| 栏 | 填什么 | 不许填什么 |
|---|---|---|
| `phenomenon` | 用户看到什么（断言层面的事实） | 形容词、"不符合预期" |
| `root_cause` | 技术根因，能锚到 `文件:行` 或具体接口/字段的就锚 | 猜测；查不到就写「未定位」并说清查到哪一步 |
| `layer` | 从 `layer_candidates` 里选一个 | 自造新词（词表与 bug-bank 同源） |
| `repro` | 能照着复现的步骤（草稿里已带真打过的请求） | 「见日志」 |

**归因查不到就写"未定位"，并说明查到哪一步为止。** 一条诚实的"未定位"比一条像模像样的
错误根因有用得多 —— 后者会让人照着它去改错的地方。

## 第三步 · 按固定六段渲染预览

`defect_draft` 的四栏是**归因结构**，TAPD 正文是**固定六段**，两者不是两套真相，是一套东西的
两种视图。对应关系如下，照这个填 `scripts/render_draft.py` 要的草稿 JSON：

| TAPD 正文段 | 从哪来 |
|---|---|
| 1 环境 | 被测实例身份：靶机 base_url、部署 commit 或镜像 digest、固件版本（旅程线抄 `intake_profile` 的构建锚） |
| 2 复现步骤 | `repro`（草稿里已带真打过的请求） |
| 3 期望结果 | 失败断言的 `expected` |
| 4 实际结果 | `phenomenon`（断言层面的事实） |
| 5 日志证据 | `evidence_refs` + **一个**主复现 log |
| 6 初步判断 | `root_cause`（含 `文件:行` 锚与一句修复方向；没定位就写「未定位」） |

`layer` 不进 TAPD 正文——它是 bug-bank 的字段，入库时用。

三条硬纪律在草稿这一层就要守住，脚本会替你把关：

1. **字段编号一律不写死**。当版实证（2026-08-12 只读 `tapd_field_config`）：工作区
   67600006 的 **bug 实体自定义字段数 = 0**，同工作区 story 实体 = 29（阳性对照）。
   所以缺陷侧本来就没有编号可填；草稿里出现 `custom_field_<数字>` 必然是从需求侧抄的
   （需求侧那些编号是给 story 排的，比如筛「测试人员」用的那一栏，与缺陷无关）。
   换项目先跑 `tapd_field_config(workspace_id, entity_type="bug")` 现场查：
   **查出来非空就停手问用户**——本仓没有经实证的缺陷自定义字段写法通道，
   官方 docstring 提到的 `cus_<别名>` 只是文档说法，没实测过，不许当机制用。
2. **六段结构禁改写**。附件清单、对照日志、优先级建议都不许另立成段；优先级是 TAPD 字段
   `priority_label`，不进正文。
3. **每缺陷只挂 1 个主复现 log**。对照日志、设备 B 的日志不是本缺陷的复现证据；
   要提就在「初步判断」里一句话带过并指向它。

跑法与判红：

```bash
python -X utf8 <skill>/scripts/render_draft.py --draft draft.json
```

exit 0 出预览；**exit 2 是被纪律闸拦下**，错误码就是原因，照着改草稿再跑。
**不要绕过脚本自己拼正文**——绕过去就等于三条纪律没人守。常见码：
`E_FIELD_NUMBER`、`E_SECTION_DRIFT`、`E_MULTI_LOG`、`E_REPRO_UNVERIFIED`、
`E_PRIORITY_IN_BODY`、`E_UNKNOWN_PROJECT`。

预览要**一条一屏**完整渲染给用户看，不要摘要成一行标题；除六段正文外还要带
标题 / 归属层 / 证据指针 / 关联需求号。

**关于项目默认值**：`field-defaults.json` 按项目分块存前缀与报告人（0027：「项目字段默认值放
skill 配置里，泛化时按项目配置」）。它带一条硬约束堵住"默认值跟着 skill 复制到别的项目、
把单提到错工作区"这个后果：**项目不在册就报 `E_UNKNOWN_PROJECT` 并要求问用户**，
不许套用别的项目的前缀与处理人。工作区、需求关联、处理人这三项，能从运行时上下文拿到的
一律以运行时为准，配置里的只是缺省。

## 第四步 · `ask_user` 确认

用 `ask_user` 出确认卡：

- **逐条勾选**，不是"全部提交"一个按钮 —— 用户常常只认其中几条；
- **默认一条都不勾**（空选是合法答案：看过并决定都不提，与"这道闸没走"必须可分）；
- 卡上写清**提交后会发生什么**（在哪个工作区建单、谁是处理人、能不能撤）；
- 处理人 `de` 在配置里默认是空的，**这一项必须问**。

用户答完之前，**不许调用任何 TAPD 写工具**。用户没答 = 没授权，不是默认允许。

> 这条通道的问答卡是真能等到答复的：「测试」capability 跑在主聊 turn 上，
> `wait_for_user_reply` 由 `deeptutor/services/session/turn_runtime.py:1620` 注入
> （锚见 `server/gateway/gate_selfcheck.py` 的 `KNOWN_CHANNELS["capability_test"]`）。
> **别照抄伙伴通道的写法**：伙伴通道故意没有等待器，在那边调问答卡会被拍平成本轮最终回复、
> 结构化答复全丢且用户无感知（BB-502）。本 skill 因此**不进伙伴的技能清单**，
> `tests/test_defect_filing_skill.py` 有一条守着这件事。

## 第五步 · 提交与回执（写工具放行后才走得到）

提交成功后回**可点开的 TAPD 链接**，并把 `submission.tapd_ref` 写回草稿。
提交失败要分清两种错并分别说：**通道不通**（我们的问题）和 **TAPD 拒绝**（字段/权限问题）——
合并成一句"提单失败"会让人查错方向。

**今天走不到这一步**：写工具没放行，所以第四步确认完就把六段正文与字段清单交给用户，
并说清单还没建。不要说"已提交""已授权""帮你提上去了"。

## 与 bug-bank 的关系

TAPD 是给项目团队看的单；`bug-bank/` 是跨项目的缺陷资产库，**两者都要**。
工作区规范：缺陷统一入 `bug-bank/` 并按其 README 资产化，修复未资产化不闭环。
本 skill 只负责 TAPD 这一侧，入库走 `bug-bank/add.py`，**不要在这里另建台账**。

## 你不做的事

- **不调任何 TAPD 写工具**。`create_bug` / `update_bug` / `create_comments` 等 17 个写工具
  在放行之前一律禁止调用；即使哪天放行了，也必须先过第四步的确认闸——这两件事同批发生。
- 不替用户拍处理人、严重程度、优先级。
- 不把同一条缺陷的多个复现场景并列进复现步骤；别的场景在第 6 段一句话带过。
- 不为了让脚本过闸而删素材——素材不够就说不够，问用户补。
- 不引用没有真实分配的单号。要写"关联需求/关联缺陷"，先确认那个号真的存在。
