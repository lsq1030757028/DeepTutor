# 需求 → 功能测试用例

本剧本配套 `test-partner` MCP 服务器的两个工具：`validate_cases`、`save_delivery`
（在 DeepTutor 里工具全名带前缀，如 `mcp_test-partner_validate_cases`，下文一律用短名）。
需求正文的获取另有一条可选通道：**TAPD MCP 工具（如已挂载）**。

工具是确定性的，编排和写作由你负责。**校验规则的唯一权威是 `validate_cases`**——
下面「写作纪律」「用例格式规格」的每条都标了它的规则编号，照着写就不会被拦。

> 关于 TAPD 工具名（M3 已接入，服务器注册名 `tapd`，官方 `mcp-server-tapd==8.0.80`）：
> 拉单条需求用 `get_stories_or_tasks`（传 `workspace_id` + 需求 id，均可从链接解析：路径里的数字段是
> workspace_id，`story` 后的长数字/`dialog_preview_id=story_...` 是需求 id）；字段含义看
> `get_stories_fields_info`。工具全名带前缀，如 `mcp_tapd_get_stories_or_tasks`。
> 除这两个外**不要主动调其它 TAPD 工具**（尤其任何 create_/update_/send_ 开头的写操作，一律禁止）。

## 工序（按顺序走，不跳步）

### 1. 拿到需求正文

三种情况，按顺序判断：

- **用户贴了 TAPD 需求链接**：先看链接里带没带具体需求 ID（story id、`dialog_preview_id` 之类）。
  带了就用 TAPD MCP 工具**直取那一条**——不拉需求列表、不报工作区统计、不做「先看看这个项目有什么」。
  链接里只有工作区没有具体需求时，才需要问用户要哪一条。
- **用户直接粘贴了需求正文**：不用调任何工具，直接进第 2 步。
- **没有 TAPD 工具，或工具报未配置凭据 / 无权限**：**降级请用户粘贴需求正文**，并如实说明原因
  （「当前没挂 TAPD 工具」或「TAPD 侧返回未授权」），把工具返回的 `message` 原样转达。
  不要假装拉取成功，更不要凭需求 ID 编内容。

拿到正文后先确认它是不是完整需求：只有标题没有正文、或正文只有一句话时，
告诉用户能拆出来的东西很有限，问他是补正文还是按现有信息先出一版粗的。

### 2. 拆解业务规则

把需求正文拆成**编号的业务规则清单**，一条规则一行，每条都要能指回原文：

| 规则号 | 业务规则 | 需求原文出处 |
| --- | --- | --- |
| R1 | 未实名用户不能提现 | 「提现前须完成实名认证」 |
| R2 | 单笔提现金额上限 5000 元 | 「单笔限额 5000」 |

- 出处写需求里的原句片段或小节标题，**不能只写「见需求」**。
- 需求没说的不许补：没写超时时间就别写「超时 30 秒」，写成「需求未定义超时行为——待确认」。
- 拆完把「需求里没说清楚的点」单列一小节（3-5 条以内），这些是后面人闸要问的候选。

### 3. 设计测试点

每条业务规则展开成测试点，**边界和异常优先于穷举正向**：

- 正向：规则成立时的主路径（一条就够，不要把同一条规则的正向拆成三条）。
- 边界：数值/长度/时间/数量的临界值（上限、上限±1、0、空）。
- 异常：不满足前置、越权、重复提交、依赖方失败。
- 状态流转：需求带状态机时，走一遍非法流转（如已取消的单再支付）。

测试点用短句列出来即可（这一步不写完整用例），并标出它覆盖的规则号，
让用户一眼看出哪条规则漏了。

### 4. 确认范围与优先级（人闸）

用 `ask_user` 问，**一次问清，一次只问一个问题**，别连环追问、也别把一堆选项甩给用户挑。
默认执行最可能的意图，只在真歧义时才问。要问就问到：

- **范围**：全部规则，还是聚焦某个功能模块 / 某条主流程？
- **深度**：只要主流程 + 关键异常，还是要把边界值铺满？
- **第 2 步列出的「需求未定义」点**：按你的默认理解写，还是先挂着标「待确认」？
- **交付格式**：默认 markdown；用户要 xlsx 或 csv 就按用户的。

用户答得含糊时，给一个默认方案让他点头，不要自己闷头开做。

**人闸放行后继续时，先把已确认的参数完整复述一遍再动工**（范围、深度、格式、待确认项的处理方式）。
中断恢复、上下文被截断时这一步能防止你按记忆里的旧参数继续。

### 5. 生成用例（聊天内先给 Markdown 预览）

按**场景级粒度**写：一个业务场景一条用例，断言写在预期结果里，不要一个断言一条用例。
聊天里用精简六字段的 Markdown 表格给用户过目：

| 编号 | 标题 | 前置条件 | 操作步骤 | 预期结果 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| TC-001 | 已实名用户提现 100 元成功 | 账户已实名，余额 ≥ 100 | 1. 进入提现页<br>2. 输入 100 元，提交 | 提现申请创建成功，状态为「处理中」；账户可用余额扣减 100 | 高 |
| TC-002 | 未实名用户提现被拦截 | 账户未实名 | 1. 进入提现页<br>2. 输入 100 元，提交 | 提交被拒，提示需先完成实名认证；余额不变（R1） | 高 |

落盘用的全字段（所属模块 / 用例类型 / 测试数据 / 关联需求）在调 `save_delivery` 时一并传，
聊天预览里不用铺开。

### 6. `validate_cases` 自检

```
validate_cases(cases=[...])
```

- 需求链路**不传 `endpoints`**——没有抓包端点清单，覆盖率一项不适用，传了反而会拿到
  W03「端点不在清单里」的噪声。
- `errors` 非空 = 未通过。**不要把校验报错原样甩给用户**，自己按 `case_id` + `field` 定向修复。
- `warnings` 不算失败，但要看：W02（步骤过多）说明该拆用例。
- 规则覆盖率靠你自己盘：第 2 步的规则号逐条比对有没有用例覆盖，缺的当场补或跟用户说明为什么不覆盖。

### 7. 定向修复一次再验

只改被点名的条目和字段，别整批重写。改完再调一次 `validate_cases`。
第二次仍然不过，就把剩余错误如实告诉用户并说明卡在哪，不要硬落盘、更不要偷偷改规则。

### 8. `save_delivery` 落盘

```
save_delivery(cases=[...], title="提现功能测试用例", format="markdown")
```

- `format` 默认 `markdown`（需求链路偏人评审）；用户点名要 `xlsx` / `csv` 就照办。
  **XMind 导出目前不支持**（PLAN 里排在 M3，服务器侧尚未实现）——用户要 XMind 就如实说没有，
  别用别的格式冒充。
- `source_fingerprint` 是给 HAR 体检报告用的，需求链路没有对应值，留空即可；
  需求出处写进用例的「关联需求」里（见下）。

### 9. 告知落盘路径与收据

把返回的 `delivery_dir`、产物文件名、`receipt.json` 里的用例条数与校验结论转达用户。
产物在**宿主机**上，用户去那个目录取文件。

## 用例格式规格

### 精简六字段（聊天展示）

| 字段 | 要求 | 校验规则 |
| --- | --- | --- |
| 编号 | 非空、全局唯一，形如 `TC-001` | E02 / E03 |
| 标题 | 非空，一句话说清「谁在什么条件下做什么，期望什么结果」 | E04 |
| 前置条件 | 字段必须在；没有前置就显式写「无」 | E05（缺字段=错）/ W01（空值=提醒） |
| 操作步骤 | 至少 1 步，字符串数组或按行分隔的字符串 | E06 |
| 预期结果 | 非空，写可判定的断言（页面/状态/数据/提示文案） | E07 |
| 优先级 | 只能是 `高` / `中` / `低` | E08 |

### 落盘全字段（列名对齐 TAPD 用例库）

`用例名称`（=标题）/ `所属模块` / `前置条件` / `用例步骤` / `预期结果` / `用例等级`（=优先级）/
`用例类型`（默认「功能测试」）/ `测试数据` / `关联端点`。

- `所属模块`填需求里的功能模块名。
- **`关联端点`这一列在需求链路复用为「关联需求」**：填需求 ID / 标题，或第 2 步的规则号（如 `R1；R3`）。
  服务器侧当前只有这九列，没有单独的「关联需求」列——照实复用，别自造列名（导入 TAPD 会对不上）。
- 编号不是 TAPD 导入列，不进表格，`save_delivery` 会把它记进 `receipt.json` 的 `case_index`
  （Markdown 产物给人评审，额外多一列编号）。

### 场景级粒度判据

- 一个业务场景一条用例，多个断言写进同一条的预期结果。
- 步骤数落在 1–15：0 步是错（E06），超过 15 步会收到粒度提醒（W02），该拆成多条。
- 别把「登录」拆成一条独立用例又在每条用例里重复——登录属于前置条件。

## 交互纪律

（来源：PLAN M3，2026-08-04 用户实测后拍板；与 `partner/SOUL.md` 共用同一套）

1. **链接带具体需求 ID 就直取那一条**。不拉需求列表、不报工作区统计、不做无关的探索性查询。
   用户给的是一条需求，就回一条需求的事。
2. **机器字段永不回显**。`conf_id`、`queryToken`、工作区内部 ID、接口错误码这类东西，
   一律转译成业务语言：不说「queryToken 失效」，说「TAPD 登录态过期了，得重新配一下凭据」。
3. **默认执行最可能的意图**。只在真歧义时提问，且一次只问一个问题——
   不许把选择成本外抛（列一堆选项让用户挑），也不许为了「稳妥」逐项确认。

## 写作纪律

1. **每条业务规则可回溯到需求原文**。第 2 步的规则清单每条都带出处；用例里凡是引用了规则的，
   在预期结果或关联需求里带上规则号。用户随时能问「这条哪来的」，你要答得出。
2. **不编造需求里没有的字段和流程**。需求没提的接口、状态、字段名、提示文案，一律不写死。
   要写测试数据就写占位（`金额=5000`、`账号=<未实名账号>`），不要虚构真实值。
   需求缺失的部分写成「需求未定义——待确认」，不要用「一般来说」填空。
3. **不写执行声明措辞**（E09，会被直接拦）。用例是**待执行的计划**，不是执行记录：
   - 禁止过去时自报：`已执行`、`实际验证`、`测试已通过`、`PASSED`；
   - 禁止未来时自述调用：`将调用`、`接下来我会调用`、`我将执行`。
   - 正常写法：步骤写「提交提现申请」，预期写「申请创建成功，状态为处理中」——陈述句，不带人称。
   - 「未执行」「尚未验证」「系统将扣减余额」这类不是执行声明，可以写。
4. **脱敏值与机器字段不得回显**。TAPD 返回里的 token、内部 ID 不进用例、不进聊天。
5. **不许自己判绿**。本链不真跑用例，用例里不能出现「结果：通过」之类的结论字段。
6. **人闸后复述已确认参数再动工**。见第 4 步——恢复失稳时这是唯一的护栏。

## 工具速查

| 工具 | 入参 | 出参要点 |
| --- | --- | --- |
| `get_stories_or_tasks`（服务器 `tapd`，如已挂载） | `workspace_id` + 需求 id（从链接解析） | 需求正文与字段；未挂载或凭据缺失时降级请用户粘贴正文 |
| `validate_cases` | `cases`（用例数组）；需求链路不传 `endpoints` | `ok` / `errors[{case_id,field,code,problem}]` / `warnings` / `summary` |
| `save_delivery` | `cases`、`title`、`format`（需求链路用 `markdown`） | `delivery_dir` / `files` / `receipt` |
