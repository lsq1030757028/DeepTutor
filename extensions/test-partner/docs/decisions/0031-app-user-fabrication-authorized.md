# 0031 · 授权在测试环境构造一个隔离 App 用户，跑通主证据核心路径

- 日期：2026-08-12
- 决策人：用户（授权写库构造身份）
- 用户选择：**「授权写一行隔离用户到库」**（AskUserQuestion，2026-08-12）
- 背景：需求核心路径 = App 用户态接口 `/api/v1/characters/custom` 建自定义角色；该接口要 App 用户态 Bearer（HS256 JWT，可伪造，见 m2-build3 第 1 步）；但建角色时 `creator_id` 须指向真实存在的 App 用户，故须先造一个用户。发码接口造用户不通（`auth_app.sms_codes` 存 `code_hash`，明文码读不回）。

## 授权范围（精确边界，超出即越权）

**授权**：向 `auth_app.users`（或其等价用户表）**写入一行**测试用户，随后签发该用户的 App JWT，用于跑通自定义角色创建的主证据链路。

**约束五条（全部强制，缺一不得动手）**：

1. **可辨识**：用户名/手机号/昵称等一切可命名字段带 `M2R3-` 前缀（与本轮其余隔离数据同前缀），让共用环境里另外 3 个测试人一眼认出这不是真用户、也不是他们的。
2. **最小写入**：只写「能让 `creator_id` 外键成立 + 能签出可用 token」所必需的字段，不塞任何业务数据；不碰任何既有行。
3. **登记**：写入的用户 id / 前缀 / 表名落证据目录（**值除外——手机号等若属敏感一并按凭据处理**），收尾时按登记清理。
4. **DB 只读锁的唯一例外**：本次写入是 m2-build3 那道机械只读锁（`default_transaction_read_only=on`）的**唯一授权豁免**，且**仅限 `auth_app.users` 这一张表的这一行 INSERT**。豁免用完即恢复只读；不得借此把整条 DB 通道改成可写，不得复用该豁免做第二次写入。
5. **收尾**：主证据跑完 + 数据处置完成后，该测试用户按登记**停用或删除**（若应用层/库无删除路径则停用并如实标残留，同 0030 的推荐角色处置口径）。

## 结论口径（红线，写进主证据交付）

- 构造身份**只用于打开 App 用户态接口的门**。**登录/注册链路本身未验**——不得把「自定义角色创建通过」表述为「用户完整流程通过」。这与 0030 栽的是同一类错（拿旁路顶替真路径），不许重犯。
- 拿到 token 后 **≥1 条写用例走 `/api/v1/characters/custom` 建韩语自定义角色**，并按 0030 实体闸自证 `requirement_entity == 实际写入实体`（这次应相等——正好验证该闸在「对」的情况下也判绿，不是恒红的摆设）。

## 凭据纪律（无例外）

- JWT 密钥（`JWT_SECRET_APP`）**只在内存中使用**，不打印、不落任何产物/日志/证据/提交/`cases.jsonl`；先确认测试环境用的是 `.env` 真值还是 `dev-app-secret` 默认值（SSH 只读看进程环境，不从代码默认值推断）。
- 签出的 token 同按凭据处理，不落盘。
- 收口前 `leak_check.py` 对整个 run 目录再跑一次，配阳性对照（把密钥形态串喂匹配函数确认判红）。

## 证伪信号

若测试环境的 App JWT 校验除签名外还查设备绑定 / 会话表 / 用户状态位（非仅 `uid` 存在），则伪造 token 会被拒——那说明「造用户 + 签 token」不足以打开门，须回到发码或真机路径。m2-build3 已实测 `Parse` 只校验 HS256+签名+有效期、token 层不查 uid，但**建角色接口是否另做用户态校验未验**，动手第一步先探这一层。
