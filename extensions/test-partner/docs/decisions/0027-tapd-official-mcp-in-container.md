## 裁定三条

### 1. DT 的 TAPD 接入 = 官方 `mcp-server-tapd`，按 0012 的 B 装进容器

- 官方 server 约 43 个工具、含全部写操作；由平台在容器内以 stdio 拉起，令牌走 MCP 条目的**环境变量**编辑器（平台自带掩码与加密引用）。
- test-partner 网关**退出 TAPD 托管**。本周 TAPD 断链的根源正是网关这个中间层没起来——落进容器这一层，中间层随之消失。
- 该项**已在 P3 队列内、且已是 M2 工程稿 DoD#3**（「0012 五条待办全部落地」），**不新立项、不新增范围**。
- 自研 `tapd-capability` 留在字段治理侧（0004 分工），**不进 DT 接入面**；其 HTTP 形态（3796）由所有者今日停掉。

### 2. 放权分两步，写权限与确认闸同批放行

- **第一步（现在）**：把现有白名单开开，但**只放只读工具**——查缺陷、查字段、查工作流。
- **第二步**：提缺陷、改状态等**写工具，与确认闸同批放行**。
- **理由（不可让步）**：先放写权限、后补流程约束，中间那段窗口期 AI 就能绕过确认直接提单。**这个口子不能开。**
- 与 0012 一致：0012 明写「沿用只读白名单，不因为搬了家就放开写操作」。本条是它的细化，不是修订。

### 3. 每用户令牌隔离：泛化阶段再拍，现在不做

官方 server 的凭据是模块级单例、且**不读请求头**（0012 已勘察实证），故 per-user 隔离在本方案下做不到。到泛化阶段两条路：推动官方支持，或启用自研方案（其 per-request 形态已验证可用）。**现在不为这件事牺牲官方 server 的工具面。**

## 缺陷提单的编排形态（0011 原则：先问 DT 有没有现成的）

**做成 DT 的一个 skill，不造流程引擎。** DT 自带 skill 机制与 `ask_user`（可暂停等用户输入），直接用。

链路：聊天里说「提个缺陷」→ AI 从会话/日志提取六段结构与标题 → 固定格式预览 → `ask_user` 等用户确认 → 提交 → 回 TAPD 链接。

- 模板从小铁资产移植；项目字段默认值放 skill 配置里（泛化时按项目配置）。
- **三条硬纪律随 skill 带过去**：字段编号现场查、六段结构禁改写、每缺陷只挂 1 个主复现 log。
- 与 M2 工程稿 §7「两项均 IN，零自动提单」**一致**——`ask_user` 人工确认后提交，不是自动提单。
