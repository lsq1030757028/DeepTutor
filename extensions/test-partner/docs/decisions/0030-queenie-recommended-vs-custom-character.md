# 0030 · 被测对象溯源纠偏：推荐角色 ≠ 自定义角色，主证据打错了对象

- 日期：2026-08-12
- 决策人：用户（业务事实）+ manager（据此纠正归因与覆盖口径）
- 影响：BB-516 归因、主证据 DoD#4 的覆盖口径、R5 判定

## 用户原话（原样保留）

> 推荐角色不支持编辑自定义语种，前端如果编辑推荐角色的配置，保存时实际走的是创建一个自定义角色的路子

## 这条事实推翻了什么

### 1. manager 给用户的「用户视角」叙述是错的

manager 上一轮把 BB-516 描述为「用户保存时提示成功、再进去看变成中文语种配韩语音色的混合态」。**该叙述不成立**——真实用户在前端编辑推荐角色时，保存走的是**创建自定义角色**的路径，不会落到我们测的那条后台建推荐角色的路上。用户根本不会看到我们看到的那个状态。

**这是重建用户体感时凭接口行为外推的典型错误**：拿到「回执 echo 韩语、回读是中文」这组数据后，manager 直接按「用户填了韩语→保存→再进来变中文」讲了故事，而没有先确认**用户到底会不会走这条路**。工作区既有纪律「判据用重建的用户体感、不用机制触发」被用反了——重建体感的前提是先确认路径成立。

### 2. 主证据打错了被测对象

0023 锁定的靶需求是《Queenie **新建自定义角色**支持韩语语音交互及男女音色》。本轮主证据用后台 admin API 建的是**推荐角色**（`recommended_characters`），两者是不同实体、不同写入路径。

施工方已如实标注边界（「后台 API 只能建推荐角色，App 侧自定义角色要 App 用户态凭据，本轮没有；不得当成用户路径已验」），**该标注是对的且救了这次**——但 manager 在向用户汇报时没有把这条边界前置，等于让一条被明确标注为「只验到同能力面」的结果，以「验到了需求」的形态呈现。

## 裁定

### A. BB-516 重新归因（不撤单，改性质与影响面）

- **不再表述为用户可见缺陷**。真实用户路径不经过该入口。
- **仍是真缺陷，性质为接口契约层**：后台 API 接受了一个它不支持的输入（推荐角色 + 自定义语种），**回 200 + 业务码 OK + 回执 echo 韩语，实际落库中文**。正确形态是**拒绝该请求**。「错误当数据」这一判断不受本纠偏影响。
- **影响面下调**：从「用户可见的混合态」改为「后台/API 使用者可见；对终端用户无直接暴露路径（当前认知）」。
- `recommended_characters.language='中文'` 与 `character_app_mappings.language='韩语'` 的不一致仍需产品确认是否设计内。

### B. 主证据覆盖口径修正

- **R5「再次进入时正确回显」不得判 covered**——本轮验的是推荐角色路径，与需求所指的自定义角色路径不同源。改判 `declared_uncovered`，原因写「被测对象不符：本轮经后台建推荐角色，需求指 App 侧自定义角色，路径不同源」。
- 其余各条逐条复核是否同病。**凡依赖「建角色」这一动作的判定一律重核**。
- 覆盖图须显式标注：**本轮未触达需求所指的真实用户路径**。

### C. 该事实入常识库

「推荐角色不支持编辑自定义语种；前端编辑推荐角色的配置，保存实际走创建自定义角色」属项目级路由约定，非一次性结论。须沉淀为可复用真相（`knowledge-cache`），避免下一轮再拿推荐角色顶替自定义角色。

## 根因（流程层，不是执行层）

第 0 步「被测对象溯源」在本轮**只做到了系统级**（确认 Queenie = QiQi 手办 = 工作区 67600006），**没做到实体级**（推荐角色 vs 自定义角色是不是同一个东西、真实写入路径是哪条）。溯源闸的判据停在「测的是不是这个系统」，没有推进到「测的是不是需求所指的那个对象和那条路径」。

**这与本线反复出现的「作用域没人核」同族，第七例**：前六例分别是写入无人读的键、测试落在闸够不到的目录、文件级扣除顺带豁免、闸颜色随 shell 变、防漂测试把漂锁死、纯函数全绿证明不了接上了；**本例是被测对象的作用域没核到实体层**。

## 待办

1. 施工方按 §B 重核覆盖图并修正 R5 判定。
2. 确认 App 侧自定义角色路径是否有可用凭据/入口；无则主证据须如实标注「需求核心路径未验」，不得以后台同能力面顶替。
3. 该事实入 knowledge-cache。
