0这份稿要解决什么，不解决什么

M1 的批次界面是施工时顺手生成的，功能齐但没经过设计——这一份补上，并且先过你的眼再动手。

这份稿管什么
每一屏用户在问什么问题，以及界面怎么用最少的东西把这个问题答掉。 屏与屏之间怎么连、走不通的时候界面说什么。
这份稿不管什么
不写产品代码，不改任何既有文件；不改后端产物契约（schema 已 v1.0.0 冻结）； 不新造视觉体系——颜色圆角字号全部从 DT 现有页面搬。

8四种异常态

每一种都按同一个模子：说清是什么坏了 + 用户还能走哪条路。缺任何一半都不算做完。

异常一 · 执行失败——"跑不起来"和"跑了没过"必须分开
没跑起来。浏览器起来了，但靶机 127.0.0.1:8047 没有响应—— 大概率是靶机没启动。一条用例都没发出去，所以这一趟没有任何结论。
对比：如果是"跑起来了但 2 条没通过"， 那不是异常，是结果——去结果表看，不在这里报错。把这两件事混成一个红框，是最常见的坏设计。
跑到一半停了。第 7 条时浏览器崩了。 前 6 条的结论已经存下来了，不会丢；从第 7 条接着跑就行，不用整批重来。
异常二 · 证据缺失（这一条最容易被当成"系统抽风"）
3 条用例跑通了，但不算通过。它们只证明了接口返回 200， 没留下能证明"页面上确实看不到别人订单"的证据。系统不肯把这种叫通过。
编号缺什么补了会变成
TC-004没有页面快照，只有接口响应挂起 → 可判通过
TC-008断言只写了状态码，没断响应内容挂起 → 可判通过
为什么不干脆判通过：判了就是假绿。 一个测试系统一旦给过假绿，它出的所有绿色都不值钱了。
异常三 · 探测项无法判定（其实不是异常，但用户会当成异常）
TC-007 没有结论，这是对的，不是坏了。 这条用例问的是"订单金额能不能填负数"——需求文档里根本没规定，所以不管跑出什么结果， 都判不出对错。它只记录一个现象：系统接受了 -100 这个金额。
用中性底色而不是黄色/红色，是刻意的—— 黄色会让人觉得"有事要处理"，可探测项本来就不要求任何人做任何事。三个按钮是可选出路，不是待办。
异常四 · trace 打不开（三个原因，说法不同）
本地查看器没起来。命令给你，终端里粘上就能开： 
python -m playwright show-trace "…\runs\r-20260811-x3f\TC-001\trace.zip"
这条用例没有 trace 文件。它在发请求之前就被拦下了 （变量没值），浏览器压根没打开，所以没有可回放的东西。这是对的。
trace 文件应该在，但找不到了。可能被清理掉了。 这一趟的结论还在，只是回放没了；要回放只能重跑。
四种异常共用一个模子：一句话说清坏在哪（用被测系统的语言，不用堆栈）， 加至少一条还能走的路。这是既有工作台设计稿定下的规矩——「禁用 + 一句解释 + 一条还能走的路， 三件缺一不可」。本稿沿用，不新立。

仍可能被判"不顺"的三处 · 我自己不确定的地方
一、四段的"用例"段可能仍显冗余。它段内三格（生成 / 采纳 / 编译）， 但对用户来说"编译"是采纳后自动发生的、不需要他知道的事。 如果你看下来觉得四段里这一段最没用，那说明该合的是三段（接入 → 用例 → 结论），不是四段—— 这是投影粒度还能再压一档的信号，改法很轻。
二、规则表主行 + 摊开行的双行结构，行数多了一倍时不知道还好不好扫。 本稿画的是 9 条规则、其中 3 条带理由行。真实需求若有 30 条规则、20 条带理由， 这张表会很长。没有做分页或分组，是刻意的——收口要求逐条看完； 但如果实测下来长到扫不动，正确的改法是"按覆盖状态分组（先红后琥珀后绿）"，不是折叠理由。
三、§1 列表与 §2 详情之间可能还差一层。 列表卡现在只说"这条要你做什么"，详情页第一行也说"轮到你了"。 两句话内容接近，可能会让人觉得点进去没拿到新东西。 真绊到了，正确的改法是让详情页第一行说得更具体（带上"12 条里有 2 条是探测性"这类只有详情页才知道的信息）， 而不是把列表卡加回去。
